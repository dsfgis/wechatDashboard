# 手动添加待办与自定义分组需求

## 1. 背景与目标

当前系统可以根据 `@我` 消息自动创建待办，也可以把一条已持久化消息手动转为待办；待办工作台支持查看、编辑、置顶、提醒、完成和按截止时间分类。当前没有不依赖消息来源的独立“手动添加待办”入口，也没有自定义待办分组。

本变更的目标是在“待办理”页面提供手动添加待办能力，并允许用户为待办选择自定义分组或在创建过程中新增分组。自定义分组用于表达用户自己的组织方式，但不取代现有的“已置顶、已逾期、今日到期、后续到期、无截止时间”等时间分类。

## 2. 已确认事实、假设与开放事项

### 2.1 已确认事实

- 项目是 Windows WPF 桌面应用，Todo 数据持久化在本地 SQLite 数据库中。
- 现有 `TodoItem.SourceMessageId` 和数据库 `todo_items.source_message_id` 均允许为空，领域注释明确空值可表示手动创建。
- 现有待办包含标题、描述、状态、优先级、截止时间、创建/更新时间、完成时间、自动创建标识和置顶标识；提醒单独持久化。
- 现有应用用例只支持“从消息创建待办”，待办理页面没有独立的手动添加入口。
- 现有活动待办按置顶和截止时间桶展示，而不是按用户自定义分组展示。
- “项目”和“自定义待办分组”是两个独立概念。本功能不复用项目数据作为待办分组。
- 用户已确认：手动添加待办时可以选择自定义分组，也可以手动新增分组。
- 用户已确认：分组可不选，此时待办归入“未分组”。
- 用户已确认：自动生成和消息转待办默认归入“未分组”，之后可以在待办详情中修改分组。
- 用户已确认：本期支持新增和选择分组，不支持分组重命名、删除和排序。
- 用户已确认：自定义分组不取代现有的时间分类。
- 工作区当前存在与本功能无关的未提交修改；本功能不得覆盖、清理或顺带提交这些修改。

### 2.2 待审批假设

以下内容未由用户逐字段指定，将作为本需求版本的默认行为随本文档一起审批：

- 手动添加入口位于“待办理”页面，打开独立的创建表单，不占用消息“转为待办”入口。
- 创建表单包含：标题、描述、优先级、截止时间、首次提醒时间和自定义分组。
- 标题必填；描述、截止时间、首次提醒时间和分组可为空；优先级默认 `P2`。
- 新待办初始状态为 `Pending`，默认不置顶、`IsAutoCreated=false`、`SourceMessageId=null`、`ProjectId=null`。
- “未分组”是空分组状态的界面文案，不创建同名数据库记录。
- 分组名称去除首尾空白后保存；空名称无效；名称按不区分大小写的方式唯一。
- 用户在创建待办过程中新增的分组会立即独立持久化并出现在分组选项中；即使随后取消待办创建，该分组仍然保留。
- 待办卡片和详情展示所属分组；手动创建且没有来源消息的待办显示来源“手动添加”，不伪造群聊、发送人或消息时间。
- 创建成功后关闭创建表单、刷新待办工作台及相关计数，并让新待办出现在其原有时间分类中。

### 2.3 开放事项

- 当前没有阻塞 `requirements.md` 审批的开放事项。若上述待审批假设需要调整，应在进入 `design.md` 前修改并重新确认本文档。

## 3. 功能需求

### REQ-001：提供独立的手动添加待办入口

系统必须在“待办理”页面提供清晰可发现的手动添加入口，并通过独立创建表单收集待办信息。该入口不得要求用户先选择或创建一条消息。

验收标准：

- AC-001：给定用户位于“待办理”页面，当用户点击“添加待办”时，系统打开手动待办创建表单。
- AC-002：给定创建表单已打开，当用户未保存而取消或关闭表单时，系统不创建待办、不创建提醒，原列表保持不变。
- AC-003：给定创建表单已打开，表单必须提供标题、描述、优先级、截止时间、首次提醒时间和分组输入，其中只有标题为必填项。

### REQ-002：校验手动待办输入并应用明确默认值

系统必须在持久化前校验手动待办输入，并在输入不完整或无效时给出可理解、可恢复的提示。

验收标准：

- AC-004：给定标题为空或只包含空白，当用户保存时，系统拒绝创建，提示标题必填，并保留用户已输入的其他内容。
- AC-005：给定标题包含首尾空白，当用户保存时，系统去除首尾空白后持久化；不得把纯空白标题写入数据库。
- AC-006：给定用户没有选择优先级以外的可选字段，当保存成功时，新待办使用 `P2`、`Pending`、未置顶、未分组且没有提醒的默认值。
- AC-007：给定截止时间格式无效，当用户保存时，系统拒绝创建并说明正确格式或输入方式。
- AC-008：给定首次提醒时间不晚于当前时间，当用户保存时，系统拒绝创建并提示提醒时间必须在未来。
- AC-009：给定截止时间和首次提醒时间均有效，系统允许提醒时间早于、等于或晚于截止时间，不额外建立未经确认的先后约束。

### REQ-003：持久化来源真实的手动待办

系统必须把手动待办作为无来源消息的独立记录持久化，不得伪造消息关联或标记为自动创建。

验收标准：

- AC-010：给定合法的手动待办输入，当保存成功时，数据库新增且只新增一条待办，其 `SourceMessageId=null`、`IsAutoCreated=false`、`Status=Pending`，其余字段与用户输入或默认值一致。
- AC-011：给定用户为新待办设置了有效首次提醒，当保存成功时，待办和首次提醒必须作为同一创建操作成功；任一持久化步骤失败时不得留下只有待办或只有提醒的部分结果。
- AC-012：给定手动待办已保存，当应用刷新或重启后，该待办仍可在活动待办列表中读取、打开详情、编辑、置顶、设置提醒和完成。
- AC-013：给定保存操作正在执行，当用户重复点击保存或命令被重复触发时，一次表单提交最多创建一条待办。

### REQ-004：新增并选择自定义待办分组

系统必须允许用户读取已有自定义分组、为手动待办选择其中一个分组，并可在手动创建流程中新增分组。

验收标准：

- AC-014：给定系统已有自定义分组，当用户打开手动待办创建表单时，分组选项列出所有已有分组，并提供“未分组”选项。
- AC-015：给定用户输入非空且未重复的分组名称，当新增成功时，分组立即持久化并成为当前表单可选择的选项。
- AC-016：给定分组名称含首尾空白，当新增成功时，系统保存去除首尾空白后的名称。
- AC-017：给定分组名称为空、只含空白或与现有名称仅大小写不同，当用户新增时，系统拒绝创建，给出明确提示，且不产生重复分组。
- AC-018：给定用户新增分组后取消待办创建，当再次打开创建表单或重启应用时，该分组仍然存在。
- AC-019：给定用户选择一个分组并保存合法待办，当读取该待办时，其分组关联与所选分组一致。
- AC-020：给定用户选择“未分组”并保存合法待办，当读取该待办时，其分组关联为空，系统不得创建名为“未分组”的实体记录。

### REQ-005：允许所有待办在详情中维护分组

自定义分组必须适用于手动待办、消息转待办和自动生成待办。系统必须允许用户在活动待办详情中设置、更换或清除分组。

验收标准：

- AC-021：给定升级前已存在的待办、升级后自动生成的待办或消息转待办，当其未被用户指定分组时，系统将其显示为“未分组”，且不改变其他字段。
- AC-022：给定任一活动待办，当用户在详情中选择一个现有分组并保存时，刷新或重启后该分组关联仍然存在。
- AC-023：给定已有分组的活动待办，当用户在详情中改选另一个分组并保存时，系统只更新该待办的分组关联，不复制待办。
- AC-024：给定已有分组的活动待办，当用户在详情中选择“未分组”并保存时，系统清除该待办的分组关联。
- AC-025：给定已完成或已忽略的待办，其分组信息必须继续保留并可见；本期不要求在只读历史状态下修改分组。

### REQ-006：展示分组且保持现有时间分类语义

系统必须在不改变现有时间分类规则的前提下展示待办所属分组。

验收标准：

- AC-026：给定一个有分组的活动待办，其待办卡片和详情必须显示真实分组名称；无分组时显示“未分组”。
- AC-027：给定一个手动创建的待办，其列表和详情来源区域显示“手动添加”，且群聊、发送人和消息时间使用诚实的无来源状态，不伪造消息内容。
- AC-028：给定待办的分组发生变化，其“已置顶、已逾期、今日到期、后续到期、无截止时间”归属只由现有置顶和截止时间规则决定，不因分组变化而改变。
- AC-029：给定一个无截止时间且属于自定义分组的待办，它仍显示在“无截止时间”分类中，同时显示其自定义分组名称。
- AC-030：给定一个已完成或已忽略的待办，已办理页面必须继续显示其分组名称或“未分组”。

### REQ-007：保证失败、并发与刷新行为可恢复

手动创建待办和新增分组的失败不得产生虚假成功状态、半成品数据或破坏现有列表。

验收标准：

- AC-031：给定数据库写入失败或操作被取消，系统显示失败提示、保留仍可恢复的表单输入，并且列表中不出现未持久化的待办或分组。
- AC-032：给定两个操作并发创建同名分组，数据库中最多保留一个不区分大小写的规范化名称；失败方收到“分组已存在”提示。
- AC-033：给定待办保存成功，工作台、活动待办数量和高优先级数量在刷新完成后反映新记录，用户无需重启应用。
- AC-034：给定分组列表读取失败，系统仍允许用户取消表单；不得把读取失败误显示成“当前没有分组”。

### REQ-008：兼容现有数据与待办路径

系统必须以可迁移、可回滚的数据变更支持分组，并保持自动建待办、消息转待办及现有待办生命周期行为。

验收标准：

- AC-035：给定包含现有待办的旧数据库，当升级初始化完成时，所有旧待办仍存在且字段值不变，新增分组关联为空。
- AC-036：给定同一消息被自动建待办或手动转待办，现有按 `SourceMessageId` 的幂等行为继续成立，不因新增分组字段创建重复待办。
- AC-037：给定待办完成、批量完成或提醒弹窗完成操作，其状态、完成时间、取消提醒和清除置顶行为保持不变，分组关联继续保留。
- AC-038：给定迁移或初始化失败，应用不得以“迁移成功”的状态继续写入不完整 schema，并必须返回可诊断错误。

## 4. 非功能需求

- NFR-001 数据完整性：待办与首次提醒的创建必须具备原子性；分组名称唯一性必须由持久化层保证，不能只依赖 UI 检查。
- NFR-002 可用性：添加入口、必填状态、默认值、校验错误和保存结果必须清晰；失败后用户不应重新输入所有有效内容。
- NFR-003 兼容性：现有 SQLite 数据库可原地升级；旧待办、自动待办、消息转待办、详情编辑、提醒和完成流程不得回归。
- NFR-004 性能：读取待办列表时不得为每条待办单独查询一次分组；分组展示应通过批量查询、连接查询或等价的有界方式完成。
- NFR-005 可维护性：手动创建用例、分组用例、持久化和 WPF 表单状态应保持职责分离，并可在不启动真实 GUI 的情况下测试核心规则。
- NFR-006 可观测性：保存和迁移失败应提供可理解的用户提示和可诊断异常，但不得记录真实待办描述等非必要内容。

## 5. 范围

### 5.1 范围内

- “待办理”页面的手动添加入口和创建表单。
- 手动待办的标题、描述、优先级、截止时间、首次提醒时间和分组输入。
- 自定义待办分组的新增、读取、选择和持久化。
- 手动、消息转入和自动待办的可空分组关联。
- 活动待办详情中的分组设置、更换和清除。
- 待办理卡片、详情及已办理页面的分组展示。
- 手动待办的诚实来源显示。
- SQLite schema 迁移、兼容性和回归验证。

### 5.2 范围外

- 分组重命名、删除、拖拽排序或自定义排序。
- 用分组替代或重构现有置顶/截止时间分类。
- 按分组筛选、折叠、统计或批量移动待办。
- 在手动添加表单中创建或选择“项目”，以及修改现有项目管理规则。
- 循环待办、子任务、附件、标签、协作共享或云同步。
- 为手动待办伪造或绑定一条来源消息。
- 改变自动建待办和消息转待办的触发或幂等规则。

## 6. 约束与依赖

- 必须沿用 WPF、现有应用服务分层和本地 SQLite 持久化架构。
- 数据变更必须通过现有数据库初始化/迁移机制执行，不要求用户删除或重建数据库。
- “未分组”必须表示空关联，而不是可与真实分组冲突的保留名称记录。
- 分组名称的规范化和不区分大小写唯一性必须在应用层与数据库层保持一致。
- 首次提醒必须复用现有提醒实体、调度和取消生命周期。
- 必须保留工作区中已有且与本功能无关的修改。
- 实现阶段遵循仓库 TDD 规则，并使用项目实际的控制台回归测试运行器验证。

## 7. 用户故事

- US-001：作为待办用户，我希望不依赖聊天消息直接创建待办，以便记录线下或临时工作。
- US-002：作为待办用户，我希望创建时设置标题、优先级、截止时间和提醒，以便立即形成可执行计划。
- US-003：作为待办用户，我希望选择已有自定义分组，以便按自己的工作语义标记待办。
- US-004：作为待办用户，我希望在创建待办时直接新增分组，以免先离开当前流程进行设置。
- US-005：作为既有待办用户，我希望以后能在详情中调整分组，同时保留原来的截止时间分类。
- US-006：作为历史数据用户，我希望升级后原有待办、自动创建和消息转换行为保持不变，以免丢失数据或产生重复项。

## 8. 成功定义

只有当 AC-001 至 AC-038 均有可复核证据、现有待办路径无回归、旧数据库迁移通过，并且后续 `design.md`、`tasks.md` 与 `check_list.md` 获得审批后，才能进入实现并最终宣称“手动添加待办与自定义分组”功能完成。仅出现“添加待办”按钮、仅能写入数据库或仅能新增分组都不构成功能完成。
