# 待办管理、项目归属、日程概览与桌面日历需求

## 1. 背景与目标

本规格最初用于补齐不依赖消息来源的“手动添加待办”和自定义分组。该范围已经落地；当前系统还具备分组颜色、批量选择、自动待办默认当天到期、主窗口日程概览和独立桌面日历。2026-08-30 至 2026-08-31 的修订把这些已由源码、自动化测试和实际 WPF 界面确认的增量行为纳入同一 Todo 功能基线。

本规格的目标是完整描述本地待办的创建、项目归属、选择、截止时间以及内嵌/桌面日历边界。2026-09-01 的待审批修订明确取消用户可见的待办分组：现有“项目设置”和“项目关键字”交互保持原样，只为新建项目增加颜色；手动待办选择已有项目，自动待办继续按项目关键字归属。项目仍不取代“已置顶、已逾期、今日到期、后续到期、无截止时间”等时间分类；日程概览和桌面日历都是同一待办数据的辅助视图，不建立第二份待办数据。

## 2. 已确认事实、假设与开放事项

### 2.1 已确认事实

- 项目是 Windows WPF 桌面应用，Todo 数据持久化在本地 SQLite 数据库中。
- 现有 `TodoItem.SourceMessageId` 和数据库 `todo_items.source_message_id` 均允许为空，领域注释明确空值可表示手动创建。
- 现有待办包含标题、描述、状态、优先级、截止时间、创建/更新时间、完成时间、自动创建标识和置顶标识；提醒单独持久化。
- 手动添加入口、创建表单、自定义分组及详情分组维护已经实现；这是当前代码现状。2026-09-01 修订以项目归属替代该分组能力，不能把旧交互继续作为目标行为。
- 现有活动待办按置顶和截止时间桶展示，而不是按用户自定义分组展示。
- 当前已实现的“项目”和“自定义待办分组”是两个独立概念：项目设置持久化在 `followed_projects`/`followed_project_keywords`，待办分组持久化在 `todo_groups`，待办还另有内部分类用的 `project_id`。这是需要迁移的现状，不是本次项目归属目标状态。
- 用户此前确认过自定义分组相关交互；这些是历史需求，不是本次目标。2026-09-01 的最新决定是取消分组，改由现有项目承担待办的用户可见归属。
- 用户已确认：项目不取代现有的时间分类。
- 当前 `todo_groups` 已通过 v4 迁移增加 `color`，固定支持灰、红、橙、绿、蓝、紫、粉七种可读色；既有分组回填灰色。
- 自动从 `@我` 消息识别的待办使用用户时区“当天最后一刻”作为默认截止时间；手动待办和用户主动从消息转换的待办保持各自输入语义。
- 待办工作台按 Todo ID 在后台刷新后恢复仍然有效的勾选状态；已经离开活动集合的待办不会保留选择。
- 主窗口已提供“桌面日历”入口；日历读取活动与已办理待办，只把有截止时间的记录按用户本地日期放入 6×7 月视图。
- 日历窗口支持透明度、尺寸和四边停靠，停靠后离开 2 秒自动缩进并保留展开把手；偏好保存在 `%LocalAppData%\WechatDashboard\desktop-calendar.json`。
- 手动创建和详情编辑中的截止时间已统一使用日期选择器及小时/分钟下拉框；清空日期表示无截止时间，新选日期默认 `23:59`，已有值保留其原时分。
- 主窗口左侧已提供“日程概览”菜单；右侧内嵌月历与桌面日历复用 `DesktopCalendarView` 和 `DesktopCalendarViewModel`。
- 当前工作区已出现单独的“待办分组设置”实现，但尚未按本次项目归属方案迁移；本轮不得把该未审批实现当成目标已经完成。
- 工作区可能存在与规格更新无关的修改；本次只允许更新四份 SDD 文档，不得覆盖、清理或顺带提交其他修改。

### 2.2 待审批假设

以下内容未由用户逐字段指定，将作为本需求版本的默认行为随本文档一起审批：

- 手动添加入口位于“待办理”页面，打开独立的创建表单，不占用消息“转为待办”入口。
- 创建表单包含：标题、描述、优先级、截止时间、首次提醒时间和项目选择。
- 标题必填；描述、截止时间、首次提醒时间和项目可为空；优先级默认 `P2`。
- 新待办初始状态为 `Pending`，默认不置顶、`IsAutoCreated=false`、`SourceMessageId=null`、`ProjectId=null`。
- “未指定项目”表示待办没有用户可见项目关联，不创建同名数据库记录。
- 项目设置与项目关键字保持当前交互：创建项目时把项目名作为初始关键字，每个项目至少保留一个关键字，可继续添加多个关键字。
- 用户在项目设置中新增的项目会立即独立持久化并出现在重新加载后的待办选项中；随后取消待办创建不会删除该项目。
- 待办卡片和详情展示所属项目；手动创建且没有来源消息的待办显示来源“手动添加”，不伪造群聊、发送人或消息时间。
- 创建成功后关闭创建表单、刷新待办工作台及相关计数，并让新待办出现在其原有时间分类中。
- REQ-009 至 REQ-014 是对当前实现的规格化记录。后续若改变色板、自动到期规则、日期输入语义、日历数据范围或停靠交互，必须先修订并重新确认四份文档。
- 用户已明确确认本轮目标：不再保留分组；项目设置和项目关键字功能保留；新建项目时增加颜色且项目列表可修改颜色；手动待办可选项目；自动待办继续按关键字归属项目。
- 用户可见实体统一称为“项目”；内部建议使用 `ManagedProjectId`（最终类型名可按代码规范调整）与现有历史分类 `ProjectId` 区分，不能把不同表的数值 ID 直接视为同一对象。
- 项目颜色沿用原分组的灰、红、橙、绿、蓝、紫、粉固定色板；新建项目必须选择颜色，默认灰色；“每个项目不同的颜色”解释为每个项目独立保存自己的颜色，不强制项目间颜色全局唯一；项目设置的颜色列使用同一固定色板下拉选项，选择后立即持久化，失败时恢复原颜色并明确提示。
- 旧分组数据采用保守迁移：与现有项目规范化同名的分组关联映射到该项目；不同名旧分组不自动创建项目或关键字，其记录保留为只读兼容数据，相关待办改为“未指定项目”，并在迁移报告中列出受影响数量。
- 项目物理删除和关键字清理行为保持现状；新增待办项目外键使用 `ON DELETE SET NULL`，删除项目后相关待办显示“未指定项目”，不得留下悬空引用或阻止现有删除操作。
- 原 `todo_items.project_id` 继续表示历史消息分类结果；新的用户可见项目关联只能按明确项目记录或规范化名称映射建立，禁止按数值 ID 碰巧相同进行映射。

## 3. 功能需求

### REQ-001：提供独立的手动添加待办入口

系统必须在“待办理”页面提供清晰可发现的手动添加入口，并通过独立创建表单收集待办信息。该入口不得要求用户先选择或创建一条消息。

验收标准：

- AC-001：给定用户位于“待办理”页面，当用户点击“添加待办”时，系统打开手动待办创建表单。
- AC-002：给定创建表单已打开，当用户未保存而取消或关闭表单时，系统不创建待办、不创建提醒，原列表保持不变。
- AC-003：给定创建表单已打开，表单必须提供标题、描述、优先级、截止时间、首次提醒时间和项目选择，其中只有标题为必填项。

### REQ-002：校验手动待办输入并应用明确默认值

系统必须在持久化前校验手动待办输入，并在输入不完整或无效时给出可理解、可恢复的提示。

验收标准：

- AC-004：给定标题为空或只包含空白，当用户保存时，系统拒绝创建，提示标题必填，并保留用户已输入的其他内容。
- AC-005：给定标题包含首尾空白，当用户保存时，系统去除首尾空白后持久化；不得把纯空白标题写入数据库。
- AC-006：给定用户没有选择优先级以外的可选字段，当保存成功时，新待办使用 `P2`、`Pending`、未置顶、未指定项目且没有提醒的默认值。
- AC-007：给定用户选择的截止日期、小时和分钟组合无法构成本地有效时间，当用户保存时，系统拒绝创建并提示重新选择；界面不得要求用户手工修正日期时间格式。
- AC-008：给定首次提醒时间不晚于当前时间，当用户保存时，系统拒绝创建并提示提醒时间必须在未来。
- AC-009：给定截止时间和首次提醒时间均有效，系统允许提醒时间早于、等于或晚于截止时间，不额外建立未经确认的先后约束。

### REQ-003：持久化来源真实的手动待办

系统必须把手动待办作为无来源消息的独立记录持久化，不得伪造消息关联或标记为自动创建。

验收标准：

- AC-010：给定合法的手动待办输入，当保存成功时，数据库新增且只新增一条待办，其 `SourceMessageId=null`、`IsAutoCreated=false`、`Status=Pending`，其余字段与用户输入或默认值一致。
- AC-011：给定用户为新待办设置了有效首次提醒，当保存成功时，待办和首次提醒必须作为同一创建操作成功；任一持久化步骤失败时不得留下只有待办或只有提醒的部分结果。
- AC-012：给定手动待办已保存，当应用刷新或重启后，该待办仍可在活动待办列表中读取、打开详情、编辑、置顶、设置提醒和完成。
- AC-013：给定保存操作正在执行，当用户重复点击保存或命令被重复触发时，一次表单提交最多创建一条待办。

### REQ-004：读取、管理并选择项目

系统必须允许用户读取项目设置中的已有项目、为手动待办选择其中一个，并通过现有项目设置入口新增；待办窗口不提供项目或分组的现场新增入口。

验收标准：

- AC-014：给定项目设置中已有项目，当用户打开手动待办创建表单时，项目选项列出所有可用项目，并提供“未指定项目”选项。
- AC-015：给定用户在项目设置中输入非空且未重复的名称并选择颜色，当新增成功时，项目和初始项目名关键字立即持久化，并在待办表单重新加载后可选。
- AC-016：给定项目名称含首尾空白，当新增成功时，系统保存去除首尾空白后的名称。
- AC-017：给定项目名称为空、只含空白或与现有名称重复，当用户新增时，系统拒绝创建，给出明确提示，且不产生重复项目或关键字。
- AC-018：给定用户在项目设置中新增项目后取消待办创建，当再次打开创建表单或重启应用时，该项目仍然存在。
- AC-019：给定用户选择一个项目并保存合法待办，当读取该待办时，其项目关联与所选项目一致。
- AC-020：给定用户选择“未指定项目”并保存合法待办，当读取该待办时，其用户可见项目关联为空，系统不得创建同名特殊项目。

### REQ-005：允许活动待办在详情中维护项目

项目归属必须适用于手动待办、消息转待办和自动生成待办。系统必须允许用户在活动待办详情中设置、更换或清除项目；自动待办的默认值仍来自项目关键字匹配。

验收标准：

- AC-021：给定升级前待办、未匹配关键字的自动待办或未指定项目的消息转待办，系统显示“未指定项目”，且不改变其他字段。
- AC-022：给定任一活动待办，当用户在详情中选择一个现有项目并保存时，刷新或重启后该项目关联仍然存在。
- AC-023：给定已有项目的活动待办，当用户在详情中改选另一个项目并保存时，系统只更新同一待办的项目关联，不复制待办。
- AC-024：给定已有项目的活动待办，当用户在详情中选择“未指定项目”并保存时，系统清除该待办的用户可见项目关联。
- AC-025：给定已完成或已忽略的待办，其项目信息必须继续保留并可见；本期不要求在只读历史状态下修改项目。

### REQ-006：在待办理等视图展示项目信息且保持时间分类语义

系统必须把“待办理”中原分组名称/颜色替换为项目名称/颜色，并在详情、已办理和日历相关视图保持一致；项目名称文字必须直接使用最新项目颜色，项目变化不得改变现有时间分类规则。

验收标准：

- AC-026：给定一个有关联项目的活动待办，“待办理”卡片或列表及详情必须显示真实项目名称，项目名称文字直接使用最新项目颜色；无项目时显示“未指定项目”，不得再显示分组信息。
- AC-027：给定一个手动创建的待办，其列表和详情来源区域显示“手动添加”，且群聊、发送人和消息时间使用诚实的无来源状态，不伪造消息内容。
- AC-028：给定待办的项目发生变化，其“已置顶、已逾期、今日到期、后续到期、无截止时间”归属只由现有置顶和截止日期规则决定，不因项目变化而改变；已逾期、今日到期、后续到期、无截止时间四组互斥且覆盖全部活动待办，置顶待办同时出现在“已置顶”组与其所属截止时间组（两处为同一行对象，勾选状态共享），顶部“活动待办”总数按去重统计，各分类计数与对应可见分组一致。
- AC-029：给定一个无截止时间且关联项目的待办，它仍显示在“无截止时间”分类中，同时显示项目名称和颜色。
- AC-030：给定一个已完成或已忽略的待办，已办理页面必须继续显示其项目名称/颜色或“未指定项目”。

### REQ-007：保证失败、并发与刷新行为可恢复

手动创建待办和项目读取/选择的失败不得产生虚假成功状态、半成品数据或破坏现有列表。

验收标准：

- AC-031：给定数据库写入失败或操作被取消，系统显示失败提示、保留仍可恢复的表单输入，并且列表中不出现未持久化的待办或项目。
- AC-032：给定两个操作并发创建同名项目，数据库中最多保留一个规范化名称及其初始关键字；失败方收到“项目已存在”提示。
- AC-033：给定待办保存成功，工作台、活动待办数量和高优先级数量在刷新完成后反映新记录，用户无需重启应用。
- AC-034：给定项目列表读取失败，系统仍允许用户取消表单；不得把读取失败误显示成“当前没有项目”。

### REQ-008：兼容现有数据与待办路径

系统必须以可迁移、可回滚的数据变更移除分组生产路径、增加项目颜色与待办项目选择，并保持自动建待办、消息转待办及现有待办生命周期行为。

验收标准：

- AC-035：给定包含现有待办的旧数据库，当升级初始化完成时，所有旧待办仍存在，项目映射遵循 AC-083、AC-084，其他字段值不变。
- AC-036：给定同一消息被自动建待办或手动转待办，现有按 `SourceMessageId` 的幂等行为继续成立，不因新增项目关联创建重复待办。
- AC-037：给定待办完成、批量完成或提醒弹窗完成操作，其状态、完成时间、取消提醒和清除置顶行为保持不变，项目关联继续保留。
- AC-038：给定迁移或初始化失败，应用不得以“迁移成功”的状态继续写入不完整 schema，并必须返回可诊断错误。

### REQ-009：为项目提供持久化可读颜色

系统必须让用户从固定可读色板中为新项目选择颜色，并允许在项目设置的颜色列通过同一色板修改既有项目颜色；项目设置、待办理、详情、已办理和后续读取必须保持最新颜色，任意外部颜色字符串不得绕过应用校验。

验收标准：

- AC-039：给定用户在项目设置中新增项目，管理入口必须提供灰、红、橙、绿、蓝、紫、粉七种预设颜色，默认选择灰色。
- AC-040：给定合法项目名称和色板颜色，当创建成功并刷新或重启后，项目名称、颜色、初始关键字及待办理项目标识保持一致。
- AC-041：给定已存在同名项目，当用户以另一颜色再次创建时，系统必须返回已有项目，且不得静默改写其原颜色。
- AC-042：给定空颜色或不在色板中的颜色，空值按默认灰色处理；其他不支持颜色必须被拒绝，且不得创建项目或初始关键字。
- AC-043：给定升级前已有项目，当项目颜色迁移完成时，既有项目获得默认灰色，迁移可重复验证且不改变项目关键字。

### REQ-010：自动识别待办默认当天到期

系统必须让从 `@我` 消息自动识别的待办默认进入用户时区的“今日到期”，避免自动任务长期落入“无截止时间”；此规则不得覆盖用户显式输入或其他待办创建路径。

验收标准：

- AC-044：给定系统在用户时区的任意时刻自动创建 `@我` 待办，新待办的 `DueAt` 等于该本地日期的最后一刻，并被 `TodoDueBucketPolicy` 归入“今日到期”。
- AC-045：给定相同 UTC 时刻和明确用户时区，日期边界计算必须只依赖注入时钟与时区；截止日期早于本地今天才属于“已逾期”，截止日期等于本地今天时无论具体时刻是否已过都属于“今日到期”，晚于今天属于“后续到期”。
- AC-046：给定手动添加待办或用户主动把消息转为待办，系统继续采用用户填写的截止时间或该路径原有默认值，不得强制套用自动识别规则。

### REQ-011：后台刷新保持有效的批量选择

系统必须以稳定 Todo ID 维护活动待办的 UI 勾选状态，使计时器、提醒或数据刷新不会无故清空用户的批量选择，同时不得把已失效选择带入批量完成。

验收标准：

- AC-047：给定用户已勾选一个或多个活动待办，当工作台刷新且这些待办仍为活动状态时，重建后的行保持相同 ID 的勾选状态。
- AC-048：给定已勾选待办在刷新前已完成、忽略或删除，当刷新完成时，该 ID 从选择集合移除，`SelectedCount` 和命令可用状态同步更新。
- AC-049：给定全选、按分类选择或“勾选项转为已办”操作，系统只处理当前活动集合中的唯一已选 ID，刷新后不得重复完成或误选其他待办。

### REQ-012：提供可停靠、可恢复的桌面待办日历

系统必须提供独立桌面日历窗口，以只读月视图展示同一仓储中的有截止时间待办，并允许打开现有待办详情。窗口必须能够停靠屏幕边缘、自动收起并恢复用户偏好，且不得创建独立待办副本。

验收标准：

- AC-050：给定主窗口已加载，当用户点击左侧“桌面日历”时，系统显示独立且不占任务栏按钮的日历窗口；重复点击复用并激活同一窗口。
- AC-051：给定日历窗口可见，月视图以星期一为首列显示固定 6×7 日期网格，支持上月、今天、下月、选择日期和手动刷新。
- AC-052：给定活动与已办理待办同时存在，日历按用户本地 `DueAt` 日期展示所有有截止时间的记录；无截止时间记录不进入日期格，但状态栏显示其数量。
- AC-053：给定同一天存在多条待办，右侧“当日日程”与日期格子预览按固定四级键排序：第一优先级（P0 最高）、第二是否关联在建（启用）项目（关联者优先）、第三消息提醒时间（有仍待触发提醒者优先，按时间升序）、第四消息发送时间（升序，无来源消息者排后）；四级键相同时以截止时间和待办 ID 稳定排序。完成状态不参与排序，已办理项保持在原位置，只通过复选框勾选状态与删除线区分，不会因完成而排到末尾、被挤出日期格子两行预览；已办理项始终完整保留在“当日日程”列表中，格子超出预览容量时仍以“还有 N 项”提示。
- AC-054：给定用户点击日历中的待办标题，系统打开现有待办详情；详情关闭后日历重新读取仓储，反映保存或状态变化。
- AC-055：给定用户调整窗口位置、大小、透明度、自动吸附开关或停靠边缘，当窗口隐藏、关闭或应用退出后再次打开时，系统从 `%LocalAppData%\WechatDashboard\desktop-calendar.json` 恢复经边界规范化的偏好。
- AC-056：给定日历已停靠任一屏幕工作区边缘，当鼠标离开 2 秒时，窗口缩进且只保留可点击展开把手；展开、缩进和重新停靠不得改变用户保存的窗口尺寸。
- AC-057：给定用户点击日历“隐藏”或窗口关闭按钮，日历只隐藏而不退出主程序；应用退出时必须停止刷新计时器、保存状态并真正关闭窗口。

### REQ-013：使用选择控件编辑待办截止日期和时间

系统必须在手动创建和待办详情中使用明确的日期、小时和分钟选择控件维护 `DueAt`，避免要求用户记忆并手工输入日期时间格式，同时继续支持无截止时间。

验收标准：

- AC-058：给定创建或详情表单已打开，截止时间区域显示日期选择器、0 至 23 小时下拉框和 0 至 59 分钟下拉框，不再以自由文本框作为主要输入方式。
- AC-059：给定日期被清空，当用户保存时，系统持久化 `DueAt=null`；给定用户新选择日期但未调整时分，界面默认使用 `23:59`。
- AC-060：给定待办已有截止时间，当详情打开时，日期、小时和分钟控件分别显示其本地值；保存后按本地时区构造 `DateTimeOffset`，无效本地时间被拒绝且不覆盖原值。

### REQ-014：在主窗口提供可复用的日程概览

系统必须在主窗口左侧提供“日程概览”导航项，并在右侧显示与桌面日历一致的月历投影；两个入口共享视图、ViewModel、仓储和详情流程，不维护平行数据。

验收标准：

- AC-061：给定主窗口已加载，当用户点击左侧“日程概览”时，右侧显示 6×7 月历、所选日期待办和状态摘要，并立即刷新当前 Todo 数据。
- AC-062：给定日程概览和桌面日历先后打开，两者复用同一 `DesktopCalendarView` 与 `DesktopCalendarViewModel`，月份、所选日期及刷新结果保持一致。
- AC-063：给定用户在任一日历入口点击待办，系统复用现有待办详情流程；详情返回后刷新同一仓储投影，不创建、复制或迁移 Todo 数据。
- AC-064：给定新增日程概览入口，原“桌面日历”按钮、独立窗口停靠、自动缩进、偏好恢复和隐藏/退出生命周期继续可用。

### REQ-015：移除用户可见的待办分组功能

系统必须取消独立待办分组设置及待办创建/详情中的分组概念。新的待办组织只使用项目；旧分组表和关联仅用于迁移、审计和回滚，不再接受新写入。

验收标准：

- AC-065：给定用户打开“关注设置”，原“项目设置”和“项目关键字”区域及行为保持，界面不再显示“待办分组设置”。
- AC-066：给定用户打开手动待办创建或详情，界面不再显示分组下拉、新增分组名称或分组颜色控件，只显示项目选择。
- AC-067：给定新建、更新、完成或读取任一待办，生产路径不再向 `todo_groups` 或 `todo_items.group_id` 写入新值。
- AC-068：给定升级前存在旧分组，升级后旧表和关联仍保留为只读兼容数据，应用不得物理删除这些历史数据或把它们继续显示为可选分组。

### REQ-016：新建和修改项目颜色

系统必须在现有项目创建流程中增加固定色板颜色选择，并把项目列表的颜色列改为同一固定色板下拉选项；用户修改颜色后立即持久化并刷新相关待办展示，同时保持项目名称、删除和项目关键字行为不变。

验收标准：

- AC-069：给定用户在“项目设置”新建项目，界面提供灰、红、橙、绿、蓝、紫、粉七种颜色并默认灰色；项目名称和初始项目名关键字仍按现有流程创建。
- AC-070：给定合法项目名称和颜色，当创建成功并刷新或重启后，项目名称、颜色及其关键字保持一致，并可供待办选择。
- AC-071：给定升级前已有项目，当迁移完成时，它获得默认灰色，既有项目 ID、名称、启用状态和全部关键字不变。
- AC-072：给定已存在同名项目，当用户以另一颜色再次创建时，系统返回已有项目且不得静默改写原颜色；非法色值不得写入。
- AC-086：给定用户在项目设置的颜色列选择另一合法颜色，系统立即更新且刷新/重启后保持新颜色，所有关联待办视图的项目名称文字同步使用新颜色；保存失败时下拉恢复原值并提示，项目名称、关键字、待办关联和匹配规则不变。

### REQ-017：手动待办选择已有项目

系统必须允许手动待办在创建和活动详情中选择现有项目或“未指定项目”，并让列表、已办理和日历显示该项目的名称与颜色。

验收标准：

- AC-073：给定项目设置中存在若干启用项目，当打开手动待办创建或活动详情时，选项恰好包含“未指定项目”和这些项目，名称与颜色和项目设置一致。
- AC-074：给定用户选择项目并保存手动待办，刷新或重启后同一待办保持该项目关联；选择“未指定项目”时关联为空。
- AC-075：给定用户在活动详情中设置、更换或清除项目，系统只更新同一待办，不复制待办，也不改变状态、提醒、置顶或截止时间桶。
- AC-076：给定项目已被一个或多个待办引用，当用户按现有项目设置流程删除该项目时，项目和关键字仍按当前行为删除，相关待办的用户可见项目关联原子清空并显示“未指定项目”，不得留下悬空引用或删除待办本身。

### REQ-018：自动待办继续按项目关键字归属

系统必须保持现有项目关键字管理规则，并让自动待办使用同一关键字匹配结果归属项目；项目颜色不改变匹配优先级或关键字语义。

验收标准：

- AC-077：给定用户新建项目，项目名继续作为初始关键字；用户可添加多个关键字，且每个项目至少保留一个关键字。
- AC-078：给定消息群名或正文命中一个项目关键字，当自动创建待办时，新待办关联该项目并显示其颜色。
- AC-079：给定多个项目关键字同时匹配，系统保持当前“最长关键字优先，再按项目名称不区分大小写排序”的唯一选择规则，颜色不参与决胜。
- AC-080：给定消息未命中任何项目关键字，自动待办保持“未指定项目”，不得按颜色、旧分组或数值 ID 推测归属。
- AC-081：给定用户修改项目关键字，后续自动待办使用更新后的规则；既有待办项目关联不被后台重写。
- AC-082：给定项目看板按项目统计，自动待办、消息匹配和看板使用同一项目名称/稳定 ID，多个群命中同一项目时只形成一个项目桶。

### REQ-019：安全迁移旧分组并保持失败可恢复

系统必须通过原子、可重复的迁移停用分组生产路径、增加项目颜色和待办项目关联，同时保留旧分组数据并避免制造未经用户配置的项目关键字。

验收标准：

- AC-083：给定旧分组与现有项目规范化同名，迁移把相关待办映射到该项目；旧分组不同名时不自动创建项目或关键字，相关待办改为“未指定项目”，旧关联保留并在迁移报告中计数。
- AC-084：给定旧 `projects.id`、`followed_projects.id` 或 `todo_groups.id` 数值相同但含义不同，迁移不得按数值相等建立项目关联，只能使用明确项目记录或规范化名称映射。
- AC-085：给定迁移重复执行、中途失败、项目/颜色读取失败或并发写入，系统不得产生重复项目、关键字、半迁移关联或虚假成功；失败时事务与迁移记录整体回滚并保留可恢复输入。

## 4. 非功能需求

- NFR-001 数据完整性：待办与首次提醒的创建必须具备原子性；项目名称、项目颜色和待办项目外键的约束必须由应用层与持久化层共同保证，不能只依赖 UI 检查。
- NFR-002 可用性：添加入口、必填状态、默认值、校验错误和保存结果必须清晰；失败后用户不应重新输入所有有效内容。
- NFR-003 兼容性：现有 SQLite 数据库可原地升级；旧待办、自动待办、消息转待办、详情编辑、提醒和完成流程不得回归。
- NFR-004 性能：读取待办列表时不得为每条待办单独查询一次项目；项目信息展示应通过批量查询、连接查询或等价的有界方式完成。
- NFR-005 可维护性：手动创建用例、项目用例、关键字匹配、持久化和 WPF 表单状态应保持职责分离，并可在不启动真实 GUI 的情况下测试核心规则。
- NFR-006 可观测性：保存和迁移失败应提供可理解的用户提示和可诊断异常，但不得记录真实待办描述等非必要内容。
- NFR-007 桌面交互：日历不得抢占独立任务栏按钮；停靠和缩进必须使用当前显示器工作区并适配 DPI 转换，不覆盖 Windows 任务栏。
- NFR-008 状态安全：日历偏好只能包含几何和显示设置，采用临时文件替换写入；读取损坏、越界或非有限数值时回退到安全默认值，不影响待办数据和应用退出。
- NFR-009 刷新性能：日历每次刷新最多读取一次活动集合和一次已办理集合；正常显示期间按分钟刷新，不建立按日期或按待办的 N+1 仓储查询。
- NFR-010 一致性：项目名称、颜色、启用状态和关键字必须以现有项目设置为事实源；待办选项、自动匹配和看板不得各自维护平行项目列表。
- NFR-011 迁移安全：迁移使用事务和版本校验和；任何名称映射、外键或数据转换失败都整体回滚，旧分组数据不做破坏性删除。
- NFR-012 性能：一次工作台或看板刷新最多各读取一次项目/关键字快照；不得按消息或待办逐条查询项目。

## 5. 范围

### 5.1 范围内

- “待办理”页面的手动添加入口和创建表单。
- 手动待办的标题、描述、优先级、截止时间、首次提醒时间和项目选择。
- 保留现有项目设置、项目关键字及其新增、读取、删除和关键字维护语义。
- 新建项目时从固定色板选择并持久化颜色；既有项目迁移为默认灰色。
- 手动、消息转入和自动待办的可空项目关联。
- 活动待办详情中的项目设置、更换和清除。
- “待办理”卡片、详情、已办理和日历相关视图的项目名称/颜色展示。
- 手动待办的诚实来源显示。
- SQLite schema 迁移、兼容性和回归验证。
- 固定色板、v4 历史分组颜色兼容以及项目颜色创建、修改和跨视图展示。
- 自动 `@我` 待办的用户时区“今日到期”默认值。
- 工作台刷新后的有效选择恢复。
- 桌面日历的月视图、详情跳转、偏好持久化、四边停靠和自动缩进。
- 创建与详情中的截止日期、小时和分钟选择控件。
- 主窗口“日程概览”内嵌月历及其与桌面日历的视图/ViewModel 复用。
- 从关注设置、待办创建和详情中移除用户可见的分组入口与字段。
- 待办创建、详情、列表、已办理、日历、消息匹配和项目看板共同使用现有项目设置记录。
- 现有 `followed_projects`、`followed_project_keywords`、`todo_groups`、`todo_items.group_id/project_id` 的无损迁移与兼容保留。

### 5.2 范围外

- 改变现有项目重命名、项目新增/删除、项目关键字新增/删除、拖拽排序或自定义排序规则。
- 用项目替代或重构现有置顶/截止时间分类。
- 按项目筛选、折叠、统计或批量移动待办。
- 在手动添加或详情表单中现场创建项目；项目创建和关键字管理只在现有项目设置入口完成。
- 循环待办、子任务、附件、标签、协作共享或云同步。
- 为手动待办伪造或绑定一条来源消息。
- 改变自动建待办和消息转待办的触发或幂等规则。
- 在日历中直接创建、拖拽改期或批量修改待办。
- 日历云同步、系统开机自启、Windows 小组件平台或跨设备共享。
- 任意颜色选择器和用户自定义色值；既有项目只允许从固定七色色板改色。
- 改变现有“新项目自动添加项目名关键字、每个项目至少保留一个关键字”的规则。
- 为不同名旧分组自动创建项目或项目关键字。
- 直接复用旧 `projects.id`、`followed_projects.id` 或 `todo_groups.id` 的数值相等关系。

## 6. 约束与依赖

- 必须沿用 WPF、现有应用服务分层和本地 SQLite 持久化架构。
- 数据变更必须通过现有数据库初始化/迁移机制执行，不要求用户删除或重建数据库。
- “未指定项目”必须表示空关联，而不是可与真实项目冲突的保留名称记录。
- 项目名称、初始项目名关键字和“至少一个关键字”的现有行为必须保持；不得为迁移而生成用户未配置的不同名项目或关键字。
- 首次提醒必须复用现有提醒实体、调度和取消生命周期。
- 必须保留工作区中已有且与本功能无关的修改。
- 实现阶段遵循仓库 TDD 规则，并使用项目实际的控制台回归测试运行器验证。
- 桌面日历只读取现有 `ITodoRepository`，偏好文件不得进入 SQLite Todo 事务，也不得包含标题、描述、消息正文或联系人信息。
- 项目设置记录必须以稳定 ID 关联待办；旧内部分类 `ProjectId` 与用户可见项目关联必须在领域和持久化命名上明确区分。
- 项目删除必须沿用现有入口和关键字清理行为；数据库通过 `ON DELETE SET NULL` 清空待办项目外键，不能级联删除待办。

## 7. 用户故事

- US-001：作为待办用户，我希望不依赖聊天消息直接创建待办，以便记录线下或临时工作。
- US-002：作为待办用户，我希望创建时设置标题、优先级、截止时间和提醒，以便立即形成可执行计划。
- US-003：作为待办用户，我希望选择项目设置中的已有项目，以便按项目标记待办。
- US-004：作为待办用户，我希望在现有项目设置中新增项目后能立即在待办中选择，以免维护两套组织数据。
- US-005：作为既有待办用户，我希望在详情中调整项目，同时保留原来的截止时间分类。
- US-006：作为历史数据用户，我希望升级后原有待办、自动创建和消息转换行为保持不变，以免丢失数据或产生重复项。
- US-007：作为待办用户，我希望用颜色快速区分项目，同时避免低对比度的任意颜色影响可读性。
- US-008：作为收到 `@我` 消息的用户，我希望自动待办默认今天到期，以便它立即进入今日工作范围。
- US-009：作为批量处理待办的用户，我希望后台刷新后仍保留有效勾选，以免重复选择。
- US-010：作为需要常驻提醒的桌面用户，我希望用可停靠、可自动收起的月历查看待办，以便不反复切回主窗口。
- US-011：作为待办用户，我希望通过日期及时间选择控件设置截止时间，以免手工输入格式错误。
- US-012：作为主窗口用户，我希望直接在“日程概览”查看月历，以免必须打开独立桌面窗口。
- US-013：作为设置用户，我希望系统不再提供待办分组，只维护现有项目和项目关键字。
- US-014：作为待办用户，我希望创建和详情中的项目选项与项目设置完全一致，以免选择到不存在的项目。
- US-015：作为消息与看板用户，我希望项目关键字、自动待办归属和统计使用同一规则，以免同一消息在不同页面归属不一致。
- US-016：作为已有数据用户，我希望同名旧分组的待办能映射到现有项目，不同名旧分组不偷偷生成项目或关键字，并保留可审计的历史数据。

## 8. 成功定义

只有当 AC-001 至 AC-086 均映射到设计、任务和检查项，现有待办与项目关键字路径无回归，v3/v4 兼容及项目颜色/待办项目迁移通过，并且 `requirements.md`、`design.md`、`tasks.md` 与 `check_list.md` 的当前版本获得统一确认后，才能把本规格作为后续实现依据。自动化通过只证明其覆盖范围；未经真实 WPF、迁移/回滚、多显示器/DPI 与重启交互证据，不得宣称项目归属或桌面日历已完成全部用户验收。
