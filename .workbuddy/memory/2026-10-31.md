## 修复一个真实的并发缺陷（原表现为偶发失败）

- 症状：`Message feed keeps the source context when a page refresh races with navigation` 偶发 `Collection was modified; enumeration operation may not execute.`
- 原因：切页自动刷新与显式"查看原始消息"会产生两个重叠的 `ShowContextAsync`，都改写共享的 `Items`；一方在 `Clear/Add` 时另一方正在 `Items.FirstOrDefault` 枚举。
- 修法（`MessageFeedViewModel`）：新增 `_itemsGate`，`ReplaceItemsAsync` 返回物化后的行并在锁内整批替换集合；`ShowContextAsync` 改为从返回的行里定位选中项，不再二次枚举 `Items`。
- 验证：连续 8 轮完整测试，每轮 97 PASS，无失败。

## 回溯邮件的正确做法（可复用）

- 回溯：把 `processing_offsets` 里 `SinopecMail.LocalCache` 的 `v1:<字节偏移>` 改小到目标邮件起始的 `From ` 分隔行，重启应用即回捞；Message-ID 去重保证重复不会重复入库。改前先 `cp` 一份 db 备份。
- 定位偏移：读文件尾部 4 MB，反向找 `\nFrom `，用 python `email.message_from_bytes` 逐段解析可先列出将回溯哪些邮件。
- **中途被杀会留下"部分入库 + 游标未推进"的状态**：每封消息是独立事务，游标只在整批成功后提交。所以进程中途退出会出现"进了 3 封、游标还在原处"，下次运行会去重补齐剩下的，不需要修数据。
- 排查这类问题时，用真实 db 的**副本**跑 `MessageCapturePipeline`（装配 `SqliteMessageProcessingUnitOfWork` + 真实 model + `MboxMailCaptureAdapter`）能拿到 `SanitizedError`；直接看 UI 或 `Debug.WriteLine` 都拿不到（Debug 输出只进调试器）。
